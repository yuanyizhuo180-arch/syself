# Syself 行动优先工作台重构设计

日期：2026-09-02  
状态：已获产品方向确认，待用户审阅本说明

## 1. 背景与目标

Syself 现有 MVP 已能完成“目标理解、路线比较、首周任务、今日执行、每日复盘”的闭环，但每个页面独立呈现，用户无法在任何页面稳定地看到当前目标、上一步的选择依据与长期进展。现有数据库也没有月目标、周目标或决策历史的一等数据模型。

本次重构面向拥有一个长期主目标、希望每天明确开始但不希望失去规划控制权的个人用户。页面的单一工作是：把长期目标转化为当日行动，同时随时说明行动为何存在、可以怎样调整。

本次交付需要达成：

1. 为所有工作区页面提供持久导航，建立仪表盘、决策路径、目标工作树、今日行动和每日复盘之间的可达链接。
2. 让目标理解、路线选择、月周目标确认、执行和重规划以不可改写的事件记录呈现，并可从任意历史节点创建新的规划分支。
3. 建立行动优先的仪表盘，第一屏只突出一项关键行动，并显示少量支撑行动、容量和近期方向。
4. 建立月目标与周目标的可持久化工作树；AI 基于已选路线提出建议，用户可采纳、创建、编辑、完成、暂停和延展节点。

## 2. 产品边界

### 包含

- 同时只允许一个活跃主目标。
- 月目标、周目标、任务的层级和状态关系。
- 以月、周、日三种粒度呈现长期方向、近期承诺和当日执行。
- AI 建议先展示、后采纳，且允许用户修改或手动创建。
- 决策原因、影响和重规划分支的回溯。
- 低能量、漏做、暂停、延展、重新规划等恢复状态。

### 不包含

- 多活跃目标、多人协作、社交目标和排行榜。
- XP、等级、火焰连续天数等游戏化主叙事。
- 强制日历连接、自动向日历写入或复杂时间盒排程。
- 未经确认的自动重规划。

## 3. 设计立场与竞品启发

采用“行动优先的工作台”。这比目标树优先或决策日志优先更符合高频使用：仪表盘先解决今天做什么，目标树提供方向，决策路径提供解释。

- 借鉴 LifePilot：缩小每日行动面，降低当日选择负担；但不把固定数量的任务设为黑箱规则。
- 借鉴 Goals 与 Tiimo：把漏做、低能量和尚未安排视为合法状态；提供补救和重排，而不是失败提示。
- 借鉴 Archion：每日焦点、阶段进度与周回顾构成闭环；但所有重排先展示影响，再由用户确认。
- 借鉴 StrideFlow：显式显示容量、固定承诺与可调整行动，保留缓冲；但允许用户从简化的时间预算开始。
- 借鉴 Sunsama：周目标不同于待办，任务始终能看见所属目标；未完成的周目标应当可延展而非消失。

视觉采用安静、低刺激的个人工作台。深绿表示当前执行，柔和绿表示完成，灰色表示未来，琥珀色表示待确认。状态不能只依赖颜色，必须同时具备文字和图标/形状。动效仅用于确认保存、树节点展开和重规划差异出现，并服从减少动效偏好。

## 4. 信息架构

```text
工作区壳层
├─ 仪表盘
│  ├─ 今天的关键行动
│  ├─ 最多 3 项支撑行动
│  ├─ 本周容量与缓冲
│  └─ 当前月/周目标摘要
├─ 决策路径
│  └─ 按时间排列的理解、选择、采纳、编辑、执行、重规划事件
├─ 目标工作树
│  └─ 主目标 → 月目标 → 周目标 → 任务
├─ 今日行动
│  └─ 完成、跳过、缩小行动、延后、暂停
└─ 每日复盘
   └─ 执行反馈、AI 洞察、下次恢复入口
```

工作区壳层在桌面端使用左侧持久导航，顶部固定显示当前主目标。手机端将其折叠为底部导航，仍保留主目标名称与当前页面。首页保留为创建或切换主目标的入口；现有 URL 不改名。

## 5. 页面职责与交互

### 仪表盘

- 首屏主操作是“开始今天的关键行动”。
- 关键行动来自当前有效分支、当前周目标和任务状态，始终展示完成标准、最低行动和预估时长。
- 支撑行动最多展示 3 项。其余任务经明确链接进入今日行动页，不在首页堆叠。
- 周容量显示已承诺分钟数、可调整分钟数和缓冲，不把容量百分比解释成绩效。
- 每张任务显示其周目标与月目标，点击可定位到目标工作树相应节点。

### 决策路径

- 每条记录固定显示：发生时间、事件类型、当时的依据、产生的影响、关联节点和可用动作。
- “重新规划”不会编辑或删除旧记录，而是以该事件为祖先创建新规划分支。
- 页面默认只强调当前有效分支；历史分支可以展开查看，且标明不再驱动仪表盘。
- 路线选择、AI 建议采纳与用户编辑必须显示差异摘要，避免自动化决定成为黑箱。

### 目标工作树

- 根节点是唯一主目标，月目标是一级子节点，周目标是月目标的子节点，任务关联到周目标。
- 每个节点可创建、编辑、完成、暂停或延展；延展会创建新的当前节点并保留原节点结果。
- AI 建议节点使用“待采纳”状态，包含它对应的已选路线阶段、成功标记、预计投入和建议理由；采纳后才加入当前工作树。
- 手动创建与编辑与 AI 建议处于同等地位，来源只是记录，不决定可编辑性。

### 今日行动与恢复

- 完成后即时更新本地界面，并异步持久化；失败时恢复原状态并给出明确重试入口。
- 用户跳过任务时选择“时间不足、精力不足、任务太难、优先级改变或其他”。系统给出三种清晰恢复动作：缩小为最低行动、移至本周可调整时段、暂停本周目标。
- 对影响多个任务的重排，先展示受影响的任务、容量和周目标，再由用户采纳。系统不得无提示自动覆盖计划。

## 6. 数据模型与持久化

在现有 `goal`、`plan_route`、`task`、`execution_event` 和 `daily_reflection` 表之上新增以下持久化对象。

### `goal_work_node`

用于月目标和周目标树。

| 字段 | 含义 |
| --- | --- |
| `id` | 节点标识 |
| `goal_id` | 所属主目标 |
| `parent_id` | 父节点；月目标为 `null` 并归属到 `goal_id`，周目标指向月目标 |
| `node_type` | `month` 或 `week` |
| `title` | 用户可编辑的节点标题 |
| `success_criteria` | 可验证完成标准 |
| `start_date` / `end_date` | 计划时间范围 |
| `status` | `suggested`、`active`、`completed`、`paused`、`carried_forward`、`archived` |
| `source` | `ai_suggestion`、`manual`、`replan` |
| `route_phase_ref` | 可选的已选路线阶段引用 |
| `branch_id` | 所属规划分支 |
| `supersedes_id` | 延展或重规划前的节点 |
| `created_at` / `updated_at` / `completed_at` | 生命周期时间 |

`task` 增加可选 `work_node_id`，以关联周目标。旧任务不会因迁移而失效；它们在树中先作为“未归属的既有任务”显示，用户或首次规划流程可将其归入周目标。

### `planning_branch`

用于标识同一主目标的可回溯规划分支。

| 字段 | 含义 |
| --- | --- |
| `id` | 分支标识 |
| `goal_id` | 所属主目标 |
| `parent_branch_id` | 重规划前的分支 |
| `base_decision_event_id` | 发起新分支的历史节点 |
| `status` | `active` 或 `superseded` |
| `reason` | 用户选择重规划的原因 |
| `created_at` | 创建时间 |

每个活跃主目标恰有一个 `active` 分支。仪表盘、今日行动和新 AI 建议只读取此分支。

### `decision_event`

这是不可变的审计记录。事件类型包括 `goal_confirmed`、`constraint_updated`、`route_selected`、`node_suggested`、`node_accepted`、`node_created`、`node_edited`、`node_completed`、`node_paused`、`node_carried_forward`、`task_recovered`、`replan_started`、`daily_reflection_saved`。

每条事件保存 `goal_id`、`branch_id`、关联节点/任务、事件前后快照 JSON、用户原因或 AI 建议依据、影响摘要和创建时间。更新目标树或重排时，必须在同一事务中写入对象更新与事件，避免“界面已变但历史缺失”。

## 7. API 与组件边界

新增 API 保持资源导向，并复用现有错误响应格式：

- `GET /api/workspace`：返回当前目标、当前分支、关键行动、支撑行动、容量和近期节点。
- `GET /api/goal-work-tree?goalId=`：返回当前分支的节点树及其任务摘要。
- `POST /api/goal-work-nodes`：创建手动节点或保存 AI 建议为待采纳节点。
- `PATCH /api/goal-work-nodes/[id]`：编辑、完成、暂停、延展或采纳节点；所有改变写入 `decision_event`。
- `POST /api/ai/goal-work-tree`：根据已选路线生成待采纳的月/周目标建议，不直接写入活跃树。
- `GET /api/decision-events?goalId=&branchId=`：按时间返回路径记录和影响摘要。
- `POST /api/replans`：返回影响预览；只有确认请求才创建新分支和更新当前状态。

页面组件保持职责单一：`WorkspaceShell` 只负责导航与目标上下文，`Dashboard` 只组合仪表盘数据，`DecisionTimeline` 只显示事件，`GoalWorkTree` 只渲染和编辑节点，恢复动作独立为 `TaskRecoveryPanel`。各客户端组件只保留必要的交互状态，数据获取与持久化逻辑通过 API 边界隔离。

## 8. 状态、错误与可访问性

- 加载态使用与最终布局一致的骨架，不以空白页面代替。
- 无活跃主目标时，工作区明确引导回首页创建目标。
- 无今日任务时，仪表盘说明当前没有承诺行动，并提供“查看本周目标”或“创建本周目标”。
- AI 生成失败、保存失败、冲突和网络重试都保留用户输入，说明下一步可做什么。
- 未来开始的节点不得误标为已完成；暂停节点不得计为失败。
- 完成、跳过和保存操作包含可读的成功反馈及恢复入口。
- 键盘可达、可见焦点、语义化导航和按钮标签为基线要求；状态使用文本与图形双重表达；减少动效偏好会禁用非必要过渡。

## 9. 验收与测试

### 行为验收

1. 任意工作区页面均能通过持久导航访问其他工作区页面。
2. 仪表盘将今天的关键行动置于最显著位置，并可追溯到所属周目标、月目标和路线选择。
3. 用户可创建、编辑、完成、暂停、延展月目标和周目标，刷新后状态仍存在。
4. AI 建议在用户采纳前不会修改活跃目标树；采纳、编辑和手动创建均写入决策路径。
5. 从历史事件重规划会创建新分支，旧分支和事件仍可阅读，仪表盘只读取新分支。
6. 跳过任务能得到温和、可执行的恢复选择；接受任何影响多项任务的调整前可看到影响预览。

### 自动化测试

- 新增数据库迁移与 D1、SQLite、Postgres 适配测试。
- 新增工作树节点、分支和不可变事件的 API 测试。
- 新增仪表盘、持久导航、决策路径、AI 建议待采纳和恢复面板的页面渲染测试。
- 为每个新增行为先编写失败测试，再实现最小功能；每次修改 JavaScript/TypeScript 后运行 `npm test`，并在完成前运行类型检查和 lint。

## 10. 实施顺序

1. 建立迁移、统一类型、数据库适配和测试基线。
2. 实现分支、目标节点和决策事件 API，完成 API 级红绿测试。
3. 实现 `WorkspaceShell` 与持久导航，迁移现有工作区页面到壳层。
4. 实现仪表盘和目标工作树，接入 AI 建议采纳与手动编辑。
5. 实现决策路径、重规划影响预览和恢复面板。
6. 完成响应式、无障碍、失败状态和全量验证。
